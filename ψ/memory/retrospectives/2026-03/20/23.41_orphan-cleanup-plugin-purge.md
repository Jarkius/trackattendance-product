## AI Diary

This session was a whack-a-mole battle with a runaway plugin. The claude-mem plugin by thedotmack has a fundamental design flaw — its bun worker daemon spawns unlimited Claude subagent processes that never terminate. Each attempt to kill them was met with the daemon instantly respawning and creating a fresh batch. It felt like fighting a hydra.

The key insight came when I realized that disabling the plugin in settings.json wasn't enough — the plugin system loads hooks from marketplace directories regardless of the enabled flag. The only reliable fix was physically removing the files from the discovery path. Even then, hooks cached in the current session's memory continued to fire, which was frustrating to explain since the user could still see errors.

What surprised me most was the sheer scale — 117 processes running since Monday, each consuming 40-55MB RAM. That's potentially 5-6GB of RAM wasted on zombie processes. The user's machine must have been noticeably sluggish. The bun worker (pid 4524) had been running for 5 days straight, endlessly spawning children that never died.

I should have gone straight to archiving the cache directory rather than trying incremental approaches (rename key, set false, etc.). The plugin's auto-recovery mechanisms defeated every soft approach.

## Honest Feedback

This session exposed a real weakness in Claude Code's plugin system — there's no clean way to disable a misbehaving plugin. Setting `enabledPlugins` to false doesn't prevent hooks from being discovered in marketplace directories. The plugin system needs a proper disable mechanism that actually stops all hook execution.

The iterative approach wasted time. I tried 4 different methods before landing on "just archive the files." In hindsight, the nuclear option was the right first move when dealing with a daemon that auto-restarts. Lesson: when something keeps respawning, remove its binary, don't just signal it.

The user was patient but clearly frustrated by the repeated "still seeing errors" reports. Each failed attempt eroded trust slightly. Better to do one thorough cleanup than five partial ones.

### Friction Points
1. **Plugin disable doesn't fully disable**: Setting enabled=false still allows hook discovery from marketplace dirs. Impact: 3 extra rounds of cleanup. Suggestion: Plugin system should respect enabled flag for all features including hooks.
2. **Cached hooks in running session**: No way to clear hooks without restarting claude. Impact: User still sees errors after cleanup. Suggestion: Hot-reload hook configuration.
3. **No plugin process management**: No built-in way to list/kill processes spawned by plugins. Impact: Had to manually identify and kill by pattern matching. Suggestion: Plugin runtime should track child PIDs.

## Lessons Learned
- **Pattern**: Runaway plugin daemons need file removal, not just configuration changes — auto-recovery defeats soft disables
- **Mistake**: Tried incremental disabling when nuclear archive was the right move from the start
- **Discovery**: Claude Code plugin hooks are discovered from marketplace directories regardless of enabled state
